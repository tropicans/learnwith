# Plan 23-01: Route-Level SSR Optimization, Hydration Safety Islands, Branded Error Boundaries & Structured Logging

## Overview

Execute Wave 1 of Phase 23: establish per-route SSR rendering strategies, guarantee client hydration safety across interactive course workspaces, implement NotebookLM-branded 404 and error recovery boundaries, and integrate structured request logging into the SSR stream handler.

<threat_model>
### Threat Modeling & Security Mitigations (ASVS Level 1)
- **T-23-03: Sensitive Header / Token Leakage in Server Request Logs**
  - *Threat:* Logging raw HTTP request URLs containing query parameters (e.g. `?passkey=...` or session tokens) or authorization headers leaks secrets into container logs or observability aggregators.
  - *Mitigation:* In `app/ssr.tsx`, extract strictly `new URL(ctx.request.url).pathname`, HTTP method, response status code, and latency in milliseconds. Never dump query strings, request bodies, or header objects into `console.log`.
- **T-23-04: Client Hydration State Poisoning / DOM Desynchronization**
  - *Threat:* Server rendering components that read browser-only globals (`window`, `localStorage`, `sessionStorage`) causes runtime `ReferenceError` crashes during SSR or severe DOM mismatch glitches on client hydration.
  - *Mitigation:* Enforce Full SSR Shell for static layout and curriculum outlines, and isolate all localStorage-dependent widgets (interactive checklists, unlock state) inside `<ClientOnly fallback={<Skeleton />}>` boundaries (per D-01).
</threat_model>
